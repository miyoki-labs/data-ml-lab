# システムの読み方と AI の使い分け

学んだことと調べたことを、技術の話だけに直して残したもの。
「確かめたこと」と「確かめていないこと」を分けて書く（分ける理由は最後の節）。

## 1. 動いているシステムを理解する地図（9領域）

初めて触るシステムは、画面から読み始めるより、先に9つの引き出しに分けて「どこが空いているか」を見る。

| 領域 | 見るもの | 最初の問い |
|---|---|---|
| 業務 | 誰が・何のために使うか | これが止まると、誰が何に困る？ |
| データ | テーブル・項目・データの流れ | この値の**正本**（正しい情報の置き場）はどこ？ |
| 画面と API | 外から入ってくる入口 | 入口は何種類ある？ |
| バッチ | 定時処理・キュー（順番待ちの箱） | いつ・何が・誰の権限で動く？ |
| 外部連携 | 他のシステムとのやりとり | 失敗したとき、相手には何が起きる？ |
| インフラ | 動いている場所・環境の数 | 開発・テスト・本番は、何が同じで何が違う？ |
| 運用・監視 | 壊れたことに気づく仕組み | 壊れたら、誰が・何で気づく？ |
| セキュリティ | 権限と秘密情報 | 秘密情報（パスワードなど）はどこに置いてある？ |
| 開発・テスト・リリース | 変更が本番に届く道 | 変更が本番に届くまでに、何が自動で何が人の手？ |

### どの現場でも通用する知識の順位

SQL → コードを入口から追う力 → HTTP と REST → バッチとキュー（**冪等性**＝同じ処理を2回走らせても結果が変わらないこと）→ git → 文字コードと日付 → クラウドの基本。
⚠️ これは参照したノートの整理で、順位を測ったものではない。SQL が先頭なのは、データの正本を直接見られるから、と読める。

## 2. 持っておく考え方（10個）

**システムを理解するための5つ**

| 考え方 | 一言でいうと |
|---|---|
| 業務の写しとして見る | システムは業務の写し。画面や表の形は、業務のやり方がそのまま出ている |
| 正本を問う | 同じ値が何か所かにあるとき、正しいのはどれか。ずれたらどれに合わせるか |
| 状態と遷移で考える | 「注文中 → 発送済み」のように、状態と、状態が変わる条件を書き出す |
| 境界を意識する | 自分の担当の内と外、システムの内と外。境界でデータや権限が変わる |
| 失敗を先に考える | うまくいく道より先に、失敗したときに何が起きて誰が気づくかを見る |

**仕事の進め方の5つ**

| 考え方 | 一言でいうと |
|---|---|
| 事実と推測を分ける | 見たことと、そうだろうと思ったことを、別の言葉で書く |
| 影響範囲を全部見る | 1か所を直す前に、その値や処理を使っている場所を探す |
| 入口から通る道をたどる | 「たぶんここ」から読まず、入口から実際に通る順に追う |
| 相手が再現できる形で伝える | 報告を読んだ人が、同じ状況をもう一度作れるだけの情報を付ける |
| 同じ失敗は仕組みで止める | 「次から気をつける」ではなく、自動で止まる・気づく形にする |

## 3. AWS の構成図の読み方

### 建物の例えで5ブロックに分ける

| ブロック | 建物の例え | 例 |
|---|---|---|
| 入口 | 玄関・受付 | 利用者が最初にたどり着く場所（ロードバランサ、公開 URL など） |
| 働く場所 | 作業室 | コンテナなどのプログラムが実際に動く場所（ECS など） |
| データ | 倉庫・金庫 | データベース、ファイル置き場（S3 など） |
| 裏方 | 管理室 | 定時処理、設定、秘密情報の保管 |
| 監視と保険 | 防犯カメラ・保険 | ログ、アラーム、バックアップ |

- 図には**描かれていない部品**がある。たとえば、外から全体を動かす司令塔（オーケストレーター）は、図の外にいることが多い。「この図に出ていないものは何か」を最初に探す。

### 操作の入口は4種類に分けられる

| 経路 | 内容 |
|---|---|
| A | 画面から人が操作する |
| B | 確認用の端末から、中身を**読むだけ**に使う |
| C | 人がいない時間に、定時バッチが自動で動く |
| D | 「環境に反映する」＝変更を各環境に届ける（デプロイ） |

障害のときは「どの経路から入った操作か」を最初に切り分けると、原因を絞りやすい。

### 設計の4つの原則

1. 中身は隠して、入口は絞る
2. 秘密情報は専用の金庫（シークレット管理）に入れ、コードや設定ファイルに書かない
3. 失敗したときの保険（ログ・アラーム・バックアップ）を最初から付ける
4. すべての環境を同じ形にして、違うのは**値だけ**にする

## 4. CI を見るときの観点

CI＝変更を入れるたびに、テストなどを自動で回す仕組み。仕組みを調べるときは、次の4つを順に聞く。

| 観点 | 聞くこと |
|---|---|
| きっかけ | 何が起きると動くか（PR の作成・ラベル・マージ後・定時） |
| 検査の中身 | PR の上で回す軽い検査と、マージ後に回す重い検査（DB・画面のテスト）は何か |
| 赤になったら | 誰が直すか。自動の修正 PR は出るか。自動でマージしてよい範囲はどこまでか |
| 環境への反映 | 開発は手動か、テスト用は自動か、本番相当は承認者が要るか |

### 確かめていないことの書き方

調べたあと、**手順書（設計）と実行履歴（実測）を並べて**、一致したものだけを「確かめたこと」にする。例：

- 確かめたこと：マージに必須の検査の一覧。マージ後に DB のテストが回ること
- 確かめていないこと：必須の検査に入っていない検査が赤でも、マージできるか。手順書にある頻度と、実行履歴の回数が合っているか。PR を出す前のローカル確認の中身

「設計はこう書いてある」と「実際にこう動いた」は別の事実。並べて書くと、未確認の部分が見える。

## 5. AI を使うときの分け方

### 会話の区切り

- 1つの会話は1つの話題にする
- 区切る前に、引き継ぎメモを書かせる
- 毎回伝える前提は、会話の外（設定ファイルなど）に置く
- 文脈量の目安：20万未満＝緑、20〜30万＝黄、30万以上＝赤の「区切りどき」。⚠️ 目安の根拠は確認していない

### モデルと effort（考える量の設定）

- 普段は中位のモデルから始め、本当に難しい課題だけ上位のモデルに上げる
- effort は推奨値から始め、自分のタスクで効果を測ってから上げる
- 「下書きは低〜中、検証は高」は**試す案**。この環境ではまだ試していない
- 会話の途中で effort を変えると、キャッシュ（前に読んだ内容の使い回し）が無効になる、と言われている。⚠️ 公式資料では確かめていない。変えなければ関係ないので、変えたいときは新しい会話で始めるのが安全
- 各社のベンチマークの数字は、自社発表が中心。**自分の実タスク10件ほどで比べて決める**

### どの AI を使うか

Claude か ChatGPT かは、工程ごとに得意が違うとされるが、最後は「自分の実タスクで両方を試して決める」に戻る。先に決め打ちしない。

## 確かめていないこと（この文書全体）

- 知識の順位、文脈量の目安、effort とキャッシュの関係は、いずれもノートや AI の回答にあった内容で、自分では測っていない
- CI の観点は、1つの仕組みを調べた経験を一般化したもの。他の CI にそのまま当てはまるとは限らない
- AWS の図の読み方は、1枚の図をもとにした整理。別の構成では、ブロックの数や経路が変わる

## 使い道

- 新しいシステムに入ったら、9領域の表を埋めて、空いている引き出しから聞く
- 構成図を渡されたら、5ブロックに分けて、「描かれていないもの」を探す
- 調べたことを報告するときは、「確かめたこと」と「確かめていないこと」を分けて書く
